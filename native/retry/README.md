# Hold and review foundation, inert

`intent-journal.mjs` is not imported by App.js, Swift, Kotlin or the page. No new production behavior or UI is enabled. It is a local, nonvisual coordinator over required ports, not a usable retry flow. The accepted readiness repair remains unchanged.

Capture is syntactic held storage, not proof of an executable or authorized action. Capture retains exact canonical JSON payload and immutable actor/person/store/date/lifecycle binding under one caller-created lowercase UUID. The record schema defines no credential fields. Callers must supply approved non-sensitive input and identifiers, never tokens or other credentials. Key-name rejection is not semantic credential-value detection. Nested credential-named fields and non-JSON values are refused. The application must supply an approved per-action input schema through verification; this module does not guess mappings from legacy action words.

Every attempt is an explicit call with the revision actually reviewed. Durable `sending` is written before transport. Uncertain outcomes require a fresh review, not automatic replay. Startup recovery only changes interrupted `sending` to `uncertain`. Earlier unresolved records block all later records conservatively, even across rooms, until conflict semantics are separately agreed. Stop retrying retains the record and ordering barrier; it is not cancellation or rollback. No expiry, pruning, overwriting or automatic supersession exists. A failed write disables that coordinator instance until storage is reopened and recovered. Corrupt records are never replaced with an empty journal.

`retireContext` permanently blocks unresolved records for a departed binding. An observed mismatch also permanently blocks attempts. Context includes a lifecycle generation that must rotate on logout/relogin, person-link changes and departures/returns between stores or days. A verifier cannot infer the absence of past context changes from current equality; the future owner must implement authoritative invalidation and lifecycle changes. Missing that contract means no integration.

## Required ports, none supplied to production

- `storage.exclusive(fn)` must hold an OS/native cross-instance and cross-process lock for the entire operation, including dispatch. `read()` returns null only for confirmed absence. `replace(bytes)` must resolve only after atomic durable replacement; errors may have uncertain write outcomes. Do not implement this with independent UserDefaults/SharedPreferences reads/writes. No lock expiry or stealing is specified. Tests use a serialized memory port and a POSIX file port with file/directory fsync, but their mutex is same-process only. Native process-death durability is untested.
- `verify(context,intent)` is a trusted adapter, not a boolean supplied by untrusted page data. It must establish current actor/person/store/day/lifecycle, verified deployed room-command support, and exact action/input compatibility. It returns `{context,identityVerified,roomCommandVerified,actionInputVerified}`. These names are local port fields, not an invented server protocol or authorization proof. Verification runs before and after durable preparation. Server remains authoritative.
- `send(intent,context)` must atomically bind the current session to that exact context at dispatch, use only `/api/room-command`, correlate the response to that operation, and return `{status,body}`. It may use ephemeral current credentials, never journal credentials or service-role keys. It must not redirect/fallback to legacy queue-action or automatically retry. A context change after dispatch cannot undo an already-sent action. The adapter must expose uncertain outcomes honestly; the coordinator has no timeout/cancellation policy. An unresolved send holds the lock and prevents later dispatch. Verification and transport must not re-enter journal methods while the lock is held. Timeout tests simulate a rejected transport promise; a separate pending-promise test confirms serialization until it settles. A production adapter needs reviewed bounded transport behavior; no automatic timeout retry or lock stealing is supplied.
- Optional `notify({operationId,state})` is a post-persistence local notification only. Failure cannot erase the journal result. It is not a page acknowledgment or receipt protocol. It runs after lock release and may reread the journal. The future UI can reread durable state on mount. No historical response row is stored or applied.

The core/page owner must coordinate the session handoff and action handlers in `src/LeadPerformanceCalculator.jsx`: verified actor/person binding, lifecycle invalidation, capability handoff and operation-aware delivery/acknowledgment. No core edits are made here. The security owner must verify deployed `/api/room-command` compatibility and action/input mappings; the supplied contract is only a local candidate. No server changes or live probes are made. Synthetic tests cover held capture, credentials/immutability, ID reuse, capability/identity refusal, every context field, sticky retirement, pre-dispatch changes, 401/403/timeouts/malformed results, same-ID explicit retry, competing coordinator instances, ordering, stop, persistence failure before/after send, recovery, notification failure, corruption, and actual fsynced local file bytes across coordinator reopening.

No real account, live service, native device, OS kill/restart, Swift/Kotlin compilation, real bridge acknowledgment or full native-to-room-command HTTP path is proven. Readiness ReactDOM checks are separate. The local UX proposal requires per-item approval before implementation and has not been published or installed into app UI.
